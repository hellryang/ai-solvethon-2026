# Kiro Spec 요청문 (붙여넣기용)

> Kiro에서 Spec 모드로 새 spec을 시작하고, 아래 구분선 사이를 그대로 붙여넣는다.
> spec 이름은 `net-savings-match`. Kiro는 steering의 `product.md`를 자동으로 읽는다.
> requirements → design → tasks 단계마다 팀이 검토한 뒤 다음 단계로 넘긴다.

---

`net-savings-match` spec을 만들어 줘. 제품 정의는 steering의 product.md를 따른다.

## 범위: 핵심 기능 3개만

1. **내 이야기 → 전남 프로젝트 추천**
   - 사용자가 자기소개 한 줄을 쓰고 [AI로 읽기]를 누른다.
   - AI는 세 가지를 줄 단위 텍스트로 돌려준다:
     - 기술: 기술 사전 안에서 최대 5개
     - 확장 기술
     - 조건: 광주 본가 출퇴근 가능 여부, 차량 여부, 근무 형태
   - 코드가 이 텍스트를 파싱해 화면 토글을 채운다. 사용자는 토글을 고칠 수 있다.
   - 코드가 가상 프로젝트 10건과의 적합도를 계산해 상위 3건을 카드로 보여 준다. 카드마다 "강남보다 월 +OO만원"을 표시한다.
   - AI가 실패하면 키워드 매칭으로 대체한다.
2. **남는 돈 + 기업 장점 비교**
   - 카드를 누르면 코드가 세 가지를 계산한다:
     - 월 순저축 (전남 프로젝트 vs 서울 강남 기준선)
     - 손익분기 X%
     - 역전 지원금 S
   - 결과는 두 줄 누적 막대(Tailwind div)와 기업 장점 태그로 보여 준다.
   - [분석 보기]를 누르면 AI가 "맞는 점 / 아쉬운 점 / 한 줄 판단" 3줄을 쓴다. 숫자는 코드가 넘긴 것만 인용한다.
3. **1~3순위 → 준비 로드맵**
   - 사용자가 회사를 최대 3개까지 순위대로 고른다.
   - 코드가 2년·5년 누적 저축을 계산해 막대로 보여 준다.
   - AI가 1·3·6개월 준비 항목, 자격증, 1년 경력의 의미를 4줄 이내로 쓴다.

## 설계 조건

- 파일 배치:
  - `backend/app/team/snapshot.py`: 지역 6곳 통계, 가상 프로젝트 10건, 기업 장점 태그, 기술 사전, 확장표. 파이썬 상수로 두고 JSON 파일이나 `data` 폴더는 쓰지 않는다
  - `calc.py`: 남는 돈, 손익분기, 역전 지원금
  - `matching.py`: 적합도
  - `routes.py`: API
  - `backend/tests/test_team_calc.py`: 계산 테스트
  - `frontend/src/`: 화면
- 계산식은 product.md의 "계산 원칙"을 그대로 쓴다. design.md에는 공식과 함께, 손으로 계산한 예시 3개를 적는다. 이 예시가 그대로 pytest 케이스가 된다:
  - 광주 본가 → 나주 출퇴근
  - 광양 현장 근처 자취
  - 강남 자취
- AI 호출은 `backend/app/ai_service.py`의 `generate_text`만 쓴다.
  - instruction은 300자 이내, 응답은 256토큰 이내, 출력은 줄 단위 텍스트다.
  - design.md에 지시문 3개의 초안과 파싱 규칙을 적는다.
- AI는 버튼을 누를 때만 호출한다. 호출 중에는 로딩을 표시하고, 실패하면 오류 메시지와 [다시 시도] 버튼을 보여 준다.
- 새 npm·pip 패키지와 새 DB 테이블을 만들지 않는다.
- 숫자 값은 아직 팀원이 수집하고 있다. `snapshot.py`에는 우선 자리표시 값과 `# TODO 출처` 주석을 두고, 값이 오면 바꾼다.

## tasks.md 조건

- task 하나는 30~60분 단위로 나눈다. 각 task에 담당 역할(화면 / API / AI·검증 / 통합·배포 / 문서·시연)과 관련 요구사항 번호를 적는다.
- 순서: snapshot·calc·pytest → API → 화면 뼈대(mock) → AI 3종 → 연결 → 서버 검증
- `calc.py`를 저장하면 pytest가 돌아가는 Kiro hook을 만드는 task를 넣는다.

## 붙여넣은 뒤 할 일

- requirements.md: 데모 시나리오 3단계(`product.md`)가 모두 수용 기준에 들어갔는지 확인한다
- design.md: 손 계산 예시 3개와 AI 지시문 3개가 있는지 확인한다. 지시문이 300자를 넘으면 줄인다
- tasks.md: 역할 칸을 실명으로 바꾸고, 각자 자기 브랜치(`feat/<이름>-<기능>`)에서 시작한다
